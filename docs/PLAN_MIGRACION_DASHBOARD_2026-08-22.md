## 1. Contexto — qué existe hoy

Investigación directa del repo (2026-08-22). El dashboard nunca fue una sola cosa: son **tres implementaciones independientes** más un god file con código muerto, y ninguna decisión formal las había resuelto hasta ahora.

**Brecha de paridad (el hallazgo que más importa para este plan):** la SPA nativa (2) tiene 5 tabs — `market`, `signals`, `portfolio`, `risk`, `crypto`. Streamlit (1) tiene 7 páginas — las mismas 4 (`market_view`, `signals`, `risk_monitor`, `portfolio`) más **`strategies`, `backtesting`, `simulator`, que no existen en la SPA**. Streamlit no se puede retirar hoy sin perder esas 3 vistas.

**Otros datos relevantes:**
- Ningún frontend consume el WebSocket autenticado que ya existe (`api/routes/websocket.py`, corregido 2026-07-26) — ambos hacen polling REST.
- No hay Jinja2, React, Vue, htmx, ni `package.json` en el repo — "aplicación web" hoy significa FastAPI sirviendo HTML/JS/CSS estático, sin build pipeline.
- Streamlit **no** está en `docker/docker-compose.yml` — retirarlo no toca la infraestructura de despliegue.
- `docs/architecture/*.md` está desactualizado: describe Streamlit como frontend principal y no menciona `static/dashboard.html`, `static/js/`, ni `api/routes/dashboard.py`.
- ~9 documentos raíz (`DEPLOYMENT.md`, `GUIA_OPERACION.md`, `INSTRUCCIONES_EJECUCION.md`, etc.) instruyen `streamlit run ...` — algunos ya desactualizados de forma independiente (`DEPLOYMENT.md:72` referencia `app/main.py`, que no existe; el archivo real es `app/dashboard.py`).

**Bugs de backend encontrados y corregidos durante la verificación en navegador (no estaban en el alcance original, pero bloqueaban las 3 páginas por completo):**
1. **`core/auth/token_blacklist.py`** — `_get_redis()` cacheaba el cliente Redis roto tras un `ping()` fallido (la asignación a `self._redis` ocurría antes del chequeo), así que la primera llamada autenticada fallaba abierto correctamente pero **toda llamada autenticada subsecuente lanzaba `redis.exceptions.ConnectionError` sin capturar → 500** en cualquier endpoint protegido, no solo los de esta fase. Corregido: solo cachea el cliente si el `ping()` tuvo éxito; `is_blacklisted()`/`add()` resetean `self._redis=None` y devuelven `False` si el comando falla después de cachear. Verificado con 2 llamadas consecutivas a `/strategies` con un JWT válido (antes: 1ª 200, 2ª 500 — ahora: ambas 200).
2. **`api/routes/simulation.py`** — `_run_simulation_job()` instanciaba `FeatureStore()` sin el `redis_url` requerido (`TypeError` inmediato, 100% de los jobs de simulación fallaban) y llamaba a `get_history()` (método `async`) de forma síncrona sin `await` ni `connect()` previo. Corregido: función ahora `async def`, instancia `FeatureStore(redis_url=get_settings().REDIS_URL)`, llama `await feature_store.connect()` y `await feature_store.get_history(...)`. Verificado: el job ahora falla con el motivo real de infraestructura (`Error 22 connecting to localhost:6379` — no hay Redis en este entorno) en vez de un `TypeError` de firma incorrecta.
3. Bug pre-existente sin relación (encontrado al balancear llaves CSS): `static/css/styles.css` tenía una `}` sobrante al final de la regla `#page-crypto iframe`, sin efecto visual (los navegadores ignoran una llave de cierre extra a nivel raíz) pero corregido de paso.

**Auth gap pre-existente — cerrado 2026-08-24, priorizado explícitamente por el usuario tras completar el porting de las 3 páginas.** Ni la SPA nativa ni Streamlit tuvieron nunca una UI de login (`st.session_state.get("token","")` siempre vacío en Streamlit, sin setter en ningún lado del código; `static/dashboard.html` nunca enviaba `Authorization` en ningún fetch). Se agregó: botón "Iniciar sesión" en `.nav-right` + modal (`#loginModal`, reusa `.modal`/`.modal-content` ya existentes) con email/password → `POST /auth/login` real; el `access_token`/`refresh_token` se guardan en `localStorage` (`trader_ia_token`/`trader_ia_refresh_token`); botón "Cerrar sesión" llama `POST /auth/logout` y limpia el storage; el label junto al botón decodifica el JWT client-side (solo para mostrar `sub (role)`, sin verificar firma) para reflejar la sesión activa. Al iniciar/cerrar sesión se refresca automáticamente la pestaña activa si es una de las 3 auth-gated. Verificado contra el backend real: `POST /auth/login` con credenciales inválidas responde `401 {"detail":"Invalid credentials"}` de forma limpia (incluso sin Postgres disponible en este entorno de verificación — `get_user_by_email` falla abierto devolviendo `None` en vez de 500); el flujo de éxito (credenciales válidas → token real → llamada autenticada) no se pudo ejercer de punta a punta en este entorno por falta de una base Postgres poblada con un usuario real, pero el contrato completo (`TokenResponse` con `access_token`/`refresh_token`/`expires_in`) coincide exactamente con lo que el cliente espera y ya se verificó por separado con un JWT generado a mano. **No incluido:** refresh automático del access token al expirar (dura 60 min; hoy si expira, las llamadas autenticadas vuelven a fallar y el usuario debe reloguear manualmente) — mejora de seguimiento, no bloqueante.

**Hecho cuando:** las 3 vistas existen como tabs en `static/dashboard.html` ✅, muestran datos reales (no placeholders) ✅ verificado con JWT real contra el backend vivo, HTML/JS/CSS sintácticamente válidos ✅, suite verde (409 passed, mismos 2 fallos/1 error preexistentes de siempre) ✅. Falta: verificación visual humana en navegador con sesión autenticada real (no se pudo automatizar sin UI de login).

### Fase 2 — Adoptar el WebSocket ya autenticado — 🟢 hecho 2026-08-25 (parcial, ver alcance real abajo)

**Corrección de alcance vs. la redacción original de este documento:** el backend solo expone `/ws/prices/{symbol}` (`api/routes/websocket.py`) — **no existe ningún WebSocket para `signals`**, ni un endpoint de señales en tiempo real de ningún tipo. **Qué se implementó** (`static/dashboard.html`): al cargar un símbolo real (no mock) con sesión iniciada, se abre `ws://.../ws/prices/{symbol}?token=<jwt>` leyendo el mismo `localStorage.trader_ia_token` del login de la Fase 1. Reconexión con backoff exponencial (1s→30s, máx. 5 intentos) si la conexión se cae inesperadamente; sin reconexión si el cierre fue deliberado (cambio de símbolo, logout). El punto `.live-dot` del topbar (antes decorativo, siempre verde fijo) ahora refleja el estado real de la conexión: gris/sin pulso cuando no hay WS activo, verde pulsante cuando sí. Sin token en `localStorage`, no se intenta conectar (evita un ciclo de rechazos 1008 contra el servidor) — mismo patrón de degradación explícita usado en toda la SPA.

**Verificación — limitación honesta del entorno de pruebas:** el contrato del endpoint se verificó de punta a punta con un cliente WebSocket de Python puro (`websockets`) contra el servidor real corriendo en este entorno: conecta, autentica el JWT, y transmite candles reales cada 2s sin errores. La integración del lado del navegador (el código JS de arriba) se revisó exhaustivamente contra ese contrato confirmado y sigue el patrón estándar de la WebSocket API sin desviaciones, pero **no se pudo verificar con clic real en un navegador**: Chromium headless vía Playwright en este entorno sandboxeado nunca resuelve conexiones `ws://` (se queda indefinidamente en `readyState=CONNECTING`, sin disparar `open`, `close` ni `error`) — confirmado que es una limitación del entorno y no del código, reproduciendo el mismo bloqueo con un WebSocket mínimo de prueba sin relación alguna con `dashboard.html`. HTTP/fetch normal sí funciona sin problema en el mismo navegador headless (así se verificaron las Fases 0/1/1b/1c), así que el problema es específico al esquema `ws://`. Recomendado: verificar manualmente en un navegador real (no headless) antes de dar esta fase por cerrada al 100%.

**Hecho cuando:** Market View recibe actualizaciones del último candle por WS sin recargar manualmente ✅ (contrato de servidor verificado, código cliente revisado y consistente con el contrato, pendiente de clic-verificación humana en navegador real por la limitación de entorno arriba descrita). Signals **no aplica** — no hay WS de señales que adoptar; sigue en fetch único como antes (no es una regresión, es lo que ya existía).
